# 真实聊天应用接入实验

整理日期：2026-10-24。真实服务实验于 2026-10-22、2026-10-23 完成。

## 材料与方法

实验引用真实 AI 聊天应用的后端场景：应用已有用户登录、角色、会话、模型代理和消息展示流程。使用隔离副本调用与手机相同的 HTTP 接口，没有访问生产用户聊天，也没有改动线上应用。

输入是固定的合成对话，助手回答来自 NVIDIA 提供的 `openai/gpt-oss-20b`；检索使用真实的 `nvidia/nemotron-3-embed-1b` embedding（2048 维）。不是预写回答，也没有用生成式 Topic Worker 或 Selector。

两次实验使用相同的问题流程，各完成 20 轮“用户消息＋真实回答”：

1. 12 轮正常聊天，围绕东京旅行、京都活动、照顾宠物、应用项目、做饭和绘画连续展开。一个主题包含多轮，不是每条消息一个独立主题。
2. 重启后端，提出 4 组旧信息追问，涉及 5 条指定旧来源。
3. 询问一项从未说过的信息。
4. 分别从其他用户、角色、会话询问原会话的私人细节。

旧信息包括东京酒店“松月旅舍”、上野、每晚 13700 日元、入住与退房时间，京都活动“南星会馆”及日期，猫“团团”对虾过敏，以及虚构项目名“晨雾”和虚构测试口令 `红杉-731`。口令只是任意测试文本，不是账号凭据、embedding ID 或内部元数据。

近期上下文最多 5 轮并有字符限制。两次适配的计数实现略有差异：前一次按约 3000 JSON 字符裁剪，封装版按 3000 消息内容字符裁剪。逐项核对确认：所有追问题的指定旧原文和答案词均不在移除记忆块后的请求中。本实验比较的是接入是否正常，不能据此作严格的性能差异归因。

## 封装前后结果

| 检查 | 封装前：beta.2，由应用编排检索与保存 | 封装后：beta.3，`createMemoryChat` 自动处理 |
| --- | ---: | ---: |
| 完成的真实 App 对话 | 20 轮 | 20 轮 |
| 指定旧来源找回 | 5/5 | 5/5 |
| 原文保存并建立索引 | 40/40 条 | 40/40 条 |
| 实际注入片段回源一致 | 15/15 | 13/13 |
| 重启恢复 | 通过 | 通过 |
| 无相关信息时不注入历史 | 1/1 | 1/1 |
| 用户、角色、会话隔离 | 3/3 | 3/3 |
| 额外生成式记忆模型调用 | 0 | 0 |

4 组完整回复均包含预设事实。封装版 App 的原有气泡规则把 `红杉-731` 拆成两行；模型原回复和 SDK 保存的文字完整。这是应用展示行为，不是检索或存储缺陷。精确词串检查在完整回复上为 11/11，在该次气泡拼接文本上为 10/11，区别保留。

这项检查不保证模型其他措辞正确。例如模型将“上野”说成“上野区”，不能据此认定其地理分类准确。

## 移除记忆的对照

分别对东京、京都两题，仅删除实际请求里的历史证据块，保留其他消息和生成参数。

- 封装前：首次两题超时，各补测一次后均回答不记得。
- 封装后：京都题回答不记得；东京题首次和一次补测均超时，没有可用对照答案，不能计为答错。

有效对照支持这些具体回答使用了注入的历史。它不是所有场景的准确率证明。

## 超时与失败

封装前主运行记录了 7 次聊天超时和 1 次 HTTP 200 空回复；封装后主运行记录了 4 次聊天超时，另一次对照补测也超时。失败记录保留，失败请求没有被计入完成对话。已有原文没有被删除。

| 观测值 | 封装前主运行 | 封装后主运行 |
| --- | ---: | ---: |
| 聊天请求，含失败和首次对照 | 28 | 25 |
| embedding 请求 | 62 | 60 |
| 已返回聊天 usage | 63887 token | 64756 token |
| 已返回 embedding usage | 3104 token | 2725 token |
| 未返回 usage 的请求 | 8 | 4 |
| 完成回合耗时中位数，含驱动器重试 | 13974ms | 18153ms |
| embedding 耗时中位数 | 1492ms | 1432ms |

这两列不包含额外对照补测、前期连通检查和中断的短运行。缺失 usage 的消耗未知，不算零。服务波动和回复长度不同，因此不能用该表声称封装更快、总费用更低或节省了某个比例的 token。

## 自动化验证与范围

真实服务实验时，封装前 App 回归测试 87 项通过；封装后 App 95 项、SDK 46 项通过。另在全新项目从安装包验证官方 OpenAI 客户端、SQLite、类型检查、普通与流式回复、重启和错误处理；这部分使用本地测试服务，不冒充真实模型实验。

2026-10-24 另补两项确定性故障测试：聊天超时后旧原文不变，重启后成功重试只保存完成的对话；embedding 超时后两条原文仍在磁盘，恢复后重开封装可用原来源编号补回索引。SDK 共 48 项测试通过。这两项是模拟故障测试，没有再次请求真实服务。

应用内部协议由薄适配层转换，SDK 接收可见对话原文。普通使用 OpenAI 客户端的后端可以直接使用公开封装。

没有测试手机 UI 点击、主动推送消息、所有服务商、长文本压力或跨数据库严格一次写入。应用与 SDK 分属两个存储时，崩溃窗口可能导致重复记录。原始私有应用、Key 和测试数据库不随报告公开。

## 其他检索材料

此前 beta.2 核心另有 200 轮合成历史、50 道查询的检索实验。35 道共同查询中，本 SDK 指定来源 Recall@5 为 33/35，固定上游对照为 21/35；双方重启恢复 400/400 条原文。这不是 200 轮真实生成对话，也不是本次封装前后对比。方法和失败案例见[既有检索报告](https://github.com/ziningshu-code/memory-system-mvp/blob/main/benchmarks-product/blind/RESULTS.md)。

## 结论

在这组真实应用场景中，封装把原先由应用实现的检索、注入和保存移到了 SDK 调用入口；旧来源恢复、原文保存和身份隔离仍按预期工作。样本小、使用单一聊天与 embedding 配置，不能宣称普遍准确率或全面兼容。
